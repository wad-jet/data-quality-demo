# Roadmap — data_quality_demo

Источник: `docs/superpowers/specs/2026-09-23-data-quality-demo-design.md`,
`docs/project-context.md`. Приоритеты: P0 — обязательно для демо, P1 — развитие,
P2 — опционально.

## MVP (P0) — базовое демо

Реализуется scaffold'ом и является первым запускаемым набором.

- Сервисы `cmd/producer` и `cmd/consumer`, RedPanda через docker-compose.
- 5 проверок качества (6 finding-типов): field_missing, type_drift,
  invalid_json, duplicate, out_of_order, lag.
- DLQ для schema-violations, findings JSONL, агрегат (stderr, slog consumer'а)
  с caught/total по ledger.
- Тесты: unit (без сети) + integration (с брокером, skip без него).

**DoD MVP:** `go build ./...`, `go vet ./...`, `go test ./...` зелёные;
integration-тест PASS при поднятом брокере; демо-прогон (≥1000 событий)
показывает caught/total ≥ 95% по каждому тегу и не пустой DLQ.

## Фаза 1 (P0): Упакковка демо — ✅ DONE (2026-09-23, merge d8e4641)

Цель: демо запускается одной командой и воспроизводимо показывается.

- Скрипт/Makefile `demo`: поднять брокер → producer → consumer → показать
  отчёт (один запуск из чистого состояния).
- Детерминированный режим: фиксированный seed и доли дефектов — одинаковый
  отчёт при каждом прогоне.
- README: quick start, флаги сервисов, интерпретация отчёта.

**DoD фазы 1:** `make demo` (или `./demo.sh`) из чистого состояния даёт
полный отчёт; README повторяется командой без расхождений; второй прогон
даёт идентичный отчёт (дет-режим).

## Фаза 2 (P1): E2E-аудит как отдельный инструмент

Цель: независимая верификация качества без пере-запуска consumer.

- `cmd/audit`: на входе ledger + findings (+ содержимое DLQ) → отчёт:
  precision/recall по каждому дефекту, содержимое DLQ по причинам,
  таймлайн находок.
- JSON-вывод отчёта (не только stdout) для последующей обработки.
- Связь с manual_docs: справочная статья по формату ledger/findings.

**DoD фазы 2:** audit сходится с агрегатом consumer на тех же данных;
unit-тесты на синтетических данных; справочная документация обновлена.

## Фаза 3 (P2): Расширение проверок и наблюдаемости

Цель: показать расширяемость архитектуры checks.

- Новые проверки: range-валидация (amount > 0), «фрост» схемы (неизвестные
  поля), пороговые проверки на частоту дефектов.
- Prometheus-метрики consumer'а: lag потребителя, частота находок по типам.
- Конфигурация порогов (lag threshold, rate лимиты) из файла/env.

**DoD фазы 3:** каждая новая проверка — в реестре + unit-тесты + видна в
отчёте; метрики доступны (локально); пороговые значения меняются без кода.

## Вне scope (non-goals, из контекста)

- Продакшн-надёжность, HA, масштабирование.
- Web UI (только консоль/файлы).
- Внешние интеграции (BI, алерты).
