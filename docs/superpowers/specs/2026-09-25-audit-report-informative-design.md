# Spec: информативный отчёт аудита (md/html)

Дата: 2026-09-25. Ветка: `feature/audit-report-informative`.
Предыстория: `2026-09-24-audit-report-readable-design.md` (человекочитаемые
md/html-отчёты), отчёт ревьюирован opus'ом как «местами непонятно»; механизм
цифр проверен по данным реального прогона (`out/ledger.jsonl`,
`out/findings.jsonl`).

## 1. Цель

Отчёт аудита (md/html) должен быть самодостаточным для инженера без
data-quality-бэкграунда: читатель понимает смысл каждой колонки, может
пересчитать цифры из отчёта и увидеть, что всё сходится, и понимает, почему
дефект — это дефект.

## 2. Ground truth: как считаются числа (проверено по данным)

Два разных счёта, используемых одновременно — и не объясняемых в отчёте:

- **Заложено** (`Total`) и **Найдено** (`Caught`) — счёт по **записям ledger**
  (пара «order + дефект»). `Caught` = сколько записей ledger этого тега имеют
  хотя бы одну подходящую запись инспектора.
- **Всего записей** (`Findings`) — счёт **записей инспектора** (findings):
  одна запись на сообщение × проверку.
- **Ложных** (`FalsePos`) — записи инспектора, чей `order_id` не входит в
  ledger этого тега (у `invalidjson` — по счёту: `max(0, F − Total)`).
- **Подтверждено** = `Findings − FalsePos`. Подтверждённая запись — чей
  `order_id` есть в ledger тега.

Ключевые свойства (инварианты, проверены по данным и коду
`internal/audit/audit.go` / `internal/report/summary.go`):

1. `Подтверждено ≥ Caught` на каждый тег: несколько сообщений одного
   order'а (повторная отправка dups'а) с одинаковым дефектом дают несколько
   подтверждённых записей при одной записи ledger. Пример из прогона:
   lag-заказы `o-000002`, `o-000251`, `o-000387` пересланы как dups с той же
   «старой» отметкой времени → по 2 lag-записи. Итого lag: `Findings 61`,
   `Caught 58`.
2. Для `invalidjson` `Подтверждено == Caught` (оба = `min(F, Total)`).
3. `K = Σ(Подтверждено) − Σ(Caught) ≥ 0` — «дополнительные записи на те же
   дефекты». В прогоне: `286 − 281 = 5` (2 у ooo, 3 у lag).
4. Расхождение «281 + 90 = 371 ≠ 376» в текущем отчёте — следствие того, что
   «реальные дефекты» названы числом записей ledger (281), а precision
   считается по записям (286 подтверждённых).
5. Кросс-срабатывание: lag-событие (старый `ts`) выглядит и как ooo → запись
   ooo с order_id lag-заказа не в ooo-ledger → считается «ложной» для ooo
   (90 в прогоне), хотя порядок реально был нарушен.

## 3. Изменения

Все новые пользовательские тексты — русский. Форматы `text` и JSON — **не
меняются** (неё non-goal, как и в предыдущей фиче). CLI-флаги, вердикт-правила
(`explain.go: Verdict`), `CheckDLQTopic` — не меняются.

### 3.1 Таблица «Дефекты по видам»

Переименование колонок (md и html):

| Было | Стало |
|---|---|
| Заложено | Заложено |
| Найдено | Найдено из заложенных |
| Recall | Recall |
| Записей | Всего записей |
| Ложных | Ложных |
| Precision | Precision |

**Порядок элементов под таблицей (фиксирован):** таблица → пометка
ooo/lag (§3.4, если условие срабатывает) → блок «Как читать колонки».

Блок «Как читать колонки»: строка-вводная **`**Как читать колонки:**`**
(md — отдельная жирная строка, html — `<p><strong>Как читать колонки:</strong></p>`)
+ 4 пункта (md: маркированный список, html: `<ul><li>…</li></ul>`):

- **Заложено** — сколько дефектов этого вида producer вживил намеренно
  (записи ledger).
- **Найдено из заложенных** — сколько из них инспектор нашёл
  (Заложено = Найдено → Recall 100%).
- **Всего записей** — все записи инспектора этого вида. Запись — на
  сообщение, а «заложено/найдено» — на дефект: один дефект может дать
  несколько записей (повторная отправка сообщения).
- **Ложных** — записи, не подтвердившиеся при сверке с ledger.

### 3.2 Секция «Что проверяли» — раскладка в 3 части

Было: `… Инспектор нашёл {Findings} записей: {Caught} — реальные дефекты,
{FalsePos} — ложные срабатывания.`

Стало:

- Абзац 1 (вставки про инспектора/записи — числительно-независимая форма;
  pre-existing «отправил … событий» не меняется — безопасно для демо-чисел):
  `Producer отправил
  {LedgerEntries} событий, из них с заложенными дефектами: {TotalDefects}.
  Инспектор (consumer — читает каждое событие и фиксирует нарушения) —
  записей всего {Findings}:`
- Список (md — маркированный список, html — `<ul><li>…</li></ul>`), пункты:
  - `{Caught} — заложенные дефекты (найдены все),`
  - `{K} — дополнительные записи на те же дефекты (повторные отправки),`
  - `{FalsePos} — ложные срабатывания (не подтвердились при сверке с ledger).`
- Абзац 2 (без зависимости от числительных): `Подтвердились записи:
  {Findings−FalsePos} из {Findings} — это и есть Precision.`
- Определение «Инспектор (consumer …)» — здесь, при первом упоминании
  (см. §3.8).

Правила:

- `K = Σ(F−FP) − Σ(Caught)` — выводится рендером из существующих полей (см. §2.3).
- Если `K <= 0` — пункт про дополнительные записи опускается (остальные
  пункты и абзац 2 остаются). Защита от будущих изменений данных.
- Если `Caught < TotalDefects` (не все найдены) — «(найдены все)» заменяется
  на «(найдено {Caught} из {TotalDefects})».
- Если `Findings == 0` — список и абзац 2 опускаются, остаётся только
  абзац 1 в виде: «… дефектами: {TotalDefects}. Записей инспектора (consumer
  — читает каждое событие и фиксирует нарушения) нет.» (определение не
  теряется).

### 3.3 Описания дефектов (`explain.go: TagDescriptions`)

Формат: «что + почему плохо». Аббревиатуры раскрыты.

- `missing` — заказ без обязательного поля (например, суммы) — корректно
  обработать его нельзя
- `dup` — повторная отправка одного заказа — без защиты от дублей заказ
  может быть обработан дважды
- `typedrift` — поле сменило тип (число стало текстом и т.п.) — потребитель,
  ожидающий число, упадёт или молча посчитает неверно
- `ooo` (out of order) — события пришли не по порядку (событие с более поздней
  отметкой времени приходит раньше события с более ранней) — состояние заказа
  соберётся неверно
- `lag` — «старое» событие: отметка времени в прошлом — обрабатывается
  «задним числом» и может перезаписать уже актуальное состояние
- `invalidjson` — некорректный JSON — сообщение не удаётся прочитать
  (без изменений)

`TagDescription` для неизвестного тега — сам тег (как сейчас).

### 3.4 Пометка о двойных срабатываниях (ooo/lag)

Было: «"Старое" событие (лаг) выглядит и как "не по порядку" — одна причина,
две записи; это ожидаемое поведение демо, а не ошибка.»

Стало:

> Событие с «старой» отметкой времени (lag) приходит и не по порядку — поэтому
> инспектор фиксирует его дважды: как lag и как ooo. Запись ooo не совпадает
> ни с одним заложенным ooo-дефектом и считается для ooo «ложной», хотя
> порядок действительно был нарушен. Это ожидаемое поведение демо, а не ошибка
> детектора.

Показывается при том же условии: какой-то тег ooo или lag имеет `FalsePos > 0`,
один раз. Место — сразу под таблицей, перед блоком «Как читать колонки»
(см. §3.1).

### 3.5 Секция «DLQ — очередь проблемных сообщений»

- «offline» → «без обращения к брокеру».
- При `DLQ.Count > 0` раскладка по видам:
  `Должно быть: 112 = 42 (missing) + 47 (typedrift) + 23 (invalidjson)
  (по находкам инспектора, без обращения к брокеру)`.
  Состав — только виды, входящие в DLQ (`checks.IsSchemaViolation`), с
  ненулевыми счётчиками `DLQ.ByReason`; счётчики по ключам-именам проверок
  (`field_missing`, …) отображаются теговыми именами (обратное отображение
  `tagToCheck`). **Порядок слагаемых фиксирован** — по `tagOrder` (в нашем
  случае missing, typedrift, invalidjson): итерация по `tagOrder` с lookup в
  `ByReason`, НЕ по map (порядок обхода map в Go случаен). Если `Count == 0`
  — раскладка не нужна.
- Добавлено одно предложение — **последним в секции** (при наличии строки
  статуса — после неё, иначе после строки «Фактически»):
  «В DLQ попадают только нарушения схемы (missing, typedrift, invalidjson);
  dup, ooo и lag — валидные сообщения, остаются в основном топике и
  фиксируются только записями инспектора.»
- «Фактически: не считалось (требуется запущенный брокер и флаг `-dlq-topic`)»
  — без изменений.

### 3.6 Секция «Таймлайн»

- Вводная строка (первой в секции):
  «Распределение записей инспектора по **времени события** — отметке в самом
  событии, а не моменту получения (для некорректного JSON отметка неизвестна —
  берётся момент получения). Всего записей: {Σ Count} — это все записи из
  раздела «Что проверяли».»
- Текст разрыва (без приравнивания величины разрыва к лагу):
  «разрыв {N}с — событий с таким временем события не было: так проявляется
  дефект «лаг» — события отправляются сейчас, но несут «прошлую» отметку
  времени, и между ними и свежими событиями образуется разрыв».
- Бары, кластеры, порог 60с — без изменений.
- Оговорка (принята осознанно): при findings с неизвестными check-ами
  (рассинхрон версий) Σ Count таймлайна может превышать `Overall.Findings`
  (таймлайн считает все findings, Overall — только известные); в демо не
  возникает, коррекцию не делаем.

### 3.7 Чеклист «Как проверять отчёт за 10 секунд»

Пункт 3 (сейчас противоречит таблице, когда у lag precision = 100%;
причина — кросс-срабатывание lag→ooo, см. §2.5/§3.4, а НЕ множественные
записи):

> Precision = 100% у всех видов, кроме ooo (и иногда lag): у них ниже 100% —
> ожидаемо: «старое» событие фиксируется и как lag, и как ooo, и запись ooo
> не совпадает с заложенными ooo-дефектами (см. пометку после таблицы). Ниже
> 100% у любого другого вида — повод разбираться.

Пункт 4 (сейчас не проверка, а отсылка; оговорка про warnings — в самом
тексте, т.к. warnings тоже попадают в вердикт):

> Сошлись пункты 1–3 и в отчёте нет предупреждений (warnings о неизвестных
> проверках/дефектах) — в шапке будет «проблем не обнаружено»; иначе шапка
> назовёт причину.

Пункты 1–2 — без изменений.

### 3.8 Термины при первом упоминании

- «Инспектор» — определён при первом упоминании в «Что проверяли» (§3.2):
  «Инспектор (consumer — читает каждое событие и фиксирует нарушения)».
- «DLQ» — в строке вердикта «сверка DLQ» расшифровка не требуется; название
  секции меняется на «## DLQ (dead-letter queue) — очередь проблемных
  сообщений» (только заголовок секции; строка вердикта без изменений).

## 4. Не меняется (non-goals)

- JSON-схема `audit-report.json` — без новых полей; выводимые величины
  вычисляются рендером из существующих.
- `text`-формат (`RenderHuman`).
- CLI-флаги, exit codes, `Verdict`, `CheckDLQTopic`, `TimelineClusters`,
  `BarWidth`, `Pct`.
- HTML-экранирование — pre-existing follow-up, не расширяем.

## 5. Тесты (TDD)

- Фикстура `sampleReportFull` — чтобы `K > 0`: dup `Findings 3, FalsePos 1`
  (подтверждено 2 при Caught 1 → K=1). Последствия для существующих ассертов
  (обновляются, не ломаются): overall `Findings 4, FalsePos 1, Precision
  3/4 (75.0%)` — строка `| Precision | … |` в md-тесте; dup-строка таблицы
  `3 | 1 | …` и precision `66.7%`. Ассерты вердикта/HTML-классов
  (metric-bad/warn/ok, «обнаружены проблемы (2)») сохраняются. В основной
  фикстуре `Caught 2 < TotalDefects 3` → ассерт «(найдено 2 из 3)».
  `Timeline` фикстуры — с `Σ Count = 4` (например, `{BucketS: 1758621600,
  Count: 2}, {BucketS: 1758621700, Count: 2}`), чтобы вводная таймлайна
  «Всего записей: 4» была правдива; тесты, перезаписывающие `r.Timeline`,
  не затрагиваются.
- `render_test.go` (md): заменить/дополнить ассерты — новые имена колонок,
  блок «Как читать колонки», раскладка: 3 пункта (с `- 1 — дополнительные
  записи на те же дефекты (повторные отправки)`) + абзац «Подтвердились
  записи: 3 из 4 — это и есть Precision.» (форма — строго по шаблону §3.2);
  отдельный маленький тест
  (Findings>0, Caught==TotalDefects, K==0, например missing 1/1/Findings 1):
  «(найдены все)» + пункта про дополнительные записи НЕТ; `TestRenderMarkdownEmptyReport`
  — ассерт «Записей инспектора (consumer …) нет»; новый заголовок DLQ
   «(dead-letter queue)» — ассерт в md- и html-тестах; ripple-ассерты
   (ломаются от текстовых правок): `TestRenderMarkdownNoOooNoteForOtherTags`
   (старая пометка «одна причина, две записи») и строка missing в
   `TestRenderMarkdownEmptyReport`; новое описание дефектов
   (хотя бы ooo/lag/missing), новая пометка ooo/lag, DLQ-раскладка по числам
  фикстуры: `Должно быть: 1 = 1 (missing) (по находкам инспектора, без
  обращения к брокеру)`, предложение «В DLQ попадают только нарушения
  схемы…», таймлайн-вводная («не моменту получения»), текст разрыва
  («несут «прошлую» отметку»), чеклист п.3 («кроме ooo») и п.4, «Инспектор
  (consumer …)».
- `render_test.go` (html): то же самое (классы/структура без изменений).
- `explain_test.go`: новые тексты `TagDescription` (6 тегов + unknown).
- Тесты text/JSON — не трогаются.
