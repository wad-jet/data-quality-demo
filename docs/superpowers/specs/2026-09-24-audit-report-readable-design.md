# Дизайн: человекочитаемый audit-отчёт (MD/HTML)

Дата: 2026-09-24. Статус: проект (для spec review и аппрува).
Исход: spike по задаче «сделать отчёт более человекочитаемым и информативным
для неподготовленного читателя»; прототип утверждён пользователем
(`/tmp/report-after.md`, в репо не входит).

## 1. Цель

Рендеры `md` и `html` от `audit-report.json` (`-from … -format md|html`)
становятся отчётом **на русском** для человека, не погружённого в детали:
с вердиктом в шапке, пояснениями метрик, легендой дефектов, человеческим
таймлайном и чеклистом самопроверки. Текущие рендеры — сырые таблицы с
терминами и unix-временем (см. spike-разбор).

## 2. Scope

**В scope:**
- `RenderMarkdown` и `RenderHTML` (`internal/audit/render.go`) — новая
  структура и язык (русский), по §4.
- Новый файл `internal/audit/explain.go` — русская легенда дефектов,
  статические пояснения метрик, функция вердикта, группировка таймлайна
  (чистые функции, без I/O).
- Тесты: `internal/audit/explain_test.go` (новый), дополнения
  `internal/audit/render_test.go`.
- Доки: `README.md` (секция «Аудит»: md/html — русские «человеческие»
  отчёты), `manual_docs/reference/audit.md` (секция «Форматы отчёта»).

**Non-goals:**
- `text`-формат (stdout, `RenderHuman`) — **не меняется** (для специалистов).
- JSON-схема — **не меняется** (все нужные данные уже есть: `overall`,
  `per_tag`, `dlq`, `dlq_topic`, `timeline`, `ledger_entries`, `warnings`).
- CLI-флаги — не меняются; отдельного флага «объясни» нет — пояснения
  всегда в md/html.
- JS/интерактивность в HTML; английский вариант md/html; CSV.

## 3. Вердикт (детерминированные правила)

Функция `Verdict(r Report) (healthy bool, problems []string)` в `explain.go`:

1. По каждому `per_tag` (`TagMetric`): `Total > 0 && Caught < Total` →
   проблема «не все дефекты вида `<tag>` найдены: caught/total = N/M».
2. Если `DLQTopic != nil && CheckDLQTopic(r.DLQ, *r.DLQTopic) != ""` →
   проблема «DLQ: расхождение (детали — из сообщения `CheckDLQTopic`)».
   Единственный источник истины для расхождения — существующая
   `CheckDLQTopic` (сверяет и `Count`, и `ByReason`, как consumer-side
   сверка). `DLQTopic == nil` — проблема НЕ ставится (нет факта для сверки).
3. Каждый элемент `Warnings` добавляется списком проблем, **кроме**
   warnings с префиксом `DLQ-сверка` — **и только если** пункт 2 добавил
   DLQ-проблему (иначе warning сохраняется как есть; один факт — одна
   проблема; build-режим `cmd/audit` ставит такой warning ровно при том же
   расхождении).
4. `healthy = len(problems) == 0`.

Шапка: healthy → «**Вердикт: проблем не обнаружено.**» + одна фраза-
обоснование (все заложенные дефекты найдены; сверка DLQ — совпадает, если
`DLQTopic` есть). Не healthy → «**Вердикт: обнаружены проблемы (N).**» + маркированный
список проблем.

## 4. Структура отчёта (md и html — один и тот же порядок секций)

1. **Заголовок** «Отчёт о качестве данных (audit)» + блок вердикта (§3).
2. **Что проверяли** — один абзац: «Producer отправил `<ledger_entries>`
   событий, из них с заложенными дефектами: `<overall.total_defects>`.
   Инспектор нашёл `<overall.findings>` записей: `<overall.caught>` —
   реальные дефекты, `<overall.false_positives>` — ложные срабатывания».
3. **Метрики простыми словами** — таблица 2 строки: Recall (значение
   `caught/total_defects (X%)` + «Доля заложенных дефектов, которые удалось
   найти») и Precision (значение `(findings − false_positives)/findings (X%)`
   + «Доля находок, которые подтвердились; остальные — ложные
   срабатывания»).
   Отображаемые `X%` берутся из полей `recall`/`precision` отчёта как есть
   (§7); подписи дробей должны воспроизводить эти значения.
4. **Дефекты по видам** — таблица: Дефект (тег) | Что это (легенда §5) |
   Заложено | Найдено | Recall | Записей | Ложных | Precision.
   Теги с `Total == 0` — recall/precision отображаются как «—» (в HTML —
   нейтральный цвет, не «провал»). После таблицы: если у `ooo` **или** `lag`
   `false_positives > 0` — пояснительный абзац (лаг-событие выглядит и как
   «не по порядку» — одна причина, две записи; это ожидаемое поведение
   демо, а не ошибка).
5. **DLQ — очередь проблемных сообщений** (N = `r.DLQ.Count`, offline —
   считается из findings, не из ledger) — «Должно быть: N (по находкам
   инспектора, offline)» / «Фактически: M (прочитано из брокера)» / статус:
   «совпадает» или «РАСХОЖДЕНИЕ» (в HTML — красный
   маркер, класс `mismatch`). Статус выводится из
   `CheckDLQTopic(r.DLQ, *r.DLQTopic)` (тот же источник, что вердикт, §3.2);
   при расхождении **на месте** (в этой секции) выводится детали из
   сообщения `CheckDLQTopic` (разбивка по причинам), а не только в вердикте.
   Если `DLQTopic == nil` — строка «Фактически: не считалось (требуется
   запущенный брокер и флаг `-dlq-topic`)».
6. **Таймлайн** — группы (кластеры) вместо списка unix-секунд:
   - кластер = последовательные баки `timeline`, разрыв между
     соседними `bucket_s` > 60с → новый кластер;
   - строка кластера: `<HH:MM:SS>–<HH:MM:SS> (время события) [бар] <сумма>`;
     время — UTC (по `bucket_s`), бар — ASCII `█`, ширина =
     `max(1, round(40 · sum / maxSum))` (`maxSum` — сумма крупнейшего
     кластера; един кластер — тоже по этой формуле);
   - между кластерами — пометка «разрыв Ns — как правило, дефект «лаг»:
     события со «старой» отметкой времени».
   - Пустой `timeline` → секция пропускается.
   - HTML: те же кластеры горизонтальными цветными полосами (div + width).
7. **Чеклист «Как проверять отчёт за 10 секунд»** — 4 пункта (recall 100%
   по всем видам; DLQ «совпадает»; precision у ooo/lag может быть < 100% —
   это ожидаемо; вердикт в шапке).
8. **Подвал** — «Сгенерировано: <generated_at, UTC> · Данные:
   <inputs.ledger>, <inputs.findings>» + сноска: машиночитаемая версия —
   `audit-report.json`, формат для специалистов — `-format text`.

## 5. Легенда дефектов (статика, `explain.go`)

| Тег | Что это |
|---|---|
| `missing` | заказ без обязательного поля |
| `dup` | повторная отправка одного заказа |
| `typedrift` | поле другого типа (число стало текстом и т.п.) |
| `ooo` | события пришли не по порядку |
| `lag` | «старое» событие (отметка времени в прошлом) |
| `invalidjson` | некорректный JSON — сообщение не удаётся прочитать |

Неизвестный тег (внешний/будущий) — строка легенды = имя тега как есть
(без выдумывания).

## 6. HTML-маркеры

Имена CSS-классов (фикс): `verdict-ok` / `verdict-bad` (banner вердикта),
`metric-ok` (зелёный), `metric-warn` (жёлтый), `metric-bad` (красный),
`mismatch` (красный, сохраняется). Применение:

- recall 100% в строке дефекта — `metric-ok`; `Caught < Total` — `metric-bad`;
  `Total == 0` — нейтральный (без класса);
- precision < 100% — `metric-warn` (с пояснением из §4.4);
- DLQ «совпадает» — `metric-ok`; «РАСХОЖДЕНИЕ» — `metric-bad` + `mismatch`;
- вердикт — цветной banner: `verdict-ok` / `verdict-bad`.
- Инлайн CSS, без JS, самодостаточный файл (как сейчас); полосы таймлайна —
  div с `width` в процентах (относительно maxSum, как ASCII-бары).

## 7. Ошибки и края

- `LoadJSON` — без изменений.
- Проценты: `X%` — одна цифра после точки (текущий формат), recall/precision
  из `Overall`/`TagMetric` как есть.
- `TotalDefects == 0` для тега — строка рисуется, вердикт-правило §3.1 её
  пропускает.
- Локализация: весь новый пользовательский текст — русский; `text`/JSON
  остаются английскими (решение пользователя).
- HTML-экранирование путей/значений — по-прежнему отсутствует (pre-existing
  follow-up, не ухудшаем; не расширяем scope).

## 8. Тесты (TDD)

- `explain_test.go`: `Verdict` — healthy / recall-проблема / DLQ-mismatch /
  warnings / `DLQTopic==nil` не ошибка / **mismatch + соответствующий
  warning в `Warnings` → ровно одна DLQ-проблема** (дедупликация §3.3) /
  **warning с префиксом `DLQ-сверка` при отсутствии DLQ-проблемы →
  сохраняется как есть** (вторая ветка §3.3) / mismatch только по
  `ByReason` при равных `Count` → проблема (через `CheckDLQTopic`); группировка кластеров (разрыв >60с, граница 60с,
  пустой, один кластер); ширина бара (`max(1, round(40·sum/maxSum))`);
  легенда (все 6 тегов + неизвестный тег).
- `render_test.go` (md): вердикт-заголовок healthy и problems; секции в
  порядке §4; строка метрик с числами (дробь воспроизводит `X%` — взять
  нетривиально округляемое отношение, например 2/3); легенда в таблице;
  тег с `Total==0` → «—»; ooo/lag-пояснение при fp>0 и отсутствие при
  fp==0; DLQ: совпадение / расхождение (с ассертом деталей
  `CheckDLQTopic` на месте, §4.5) / `DLQTopic==nil`; таймлайн: кластер +
  пометка разрыва; пустой таймлайн → секции нет; подвал с inputs.
- `render_test.go` (html): то же самое (ключевые маркеры: banner вердикта,
  классы `metric-*`/`verdict-*`/`mismatch`, полосы таймлайна в %).
- **Существующие 6 md/html-тестов** (`TestRenderMarkdown`,
  `TestRenderMarkdownDLQTopic`, `TestRenderMarkdownTimeline`,
  `TestRenderHTML`, `TestRenderHTMLDLQTopic`, `TestRenderHTMLTimeline`)
  ассертят старую структуру — **заменяются** новыми по списку выше (имена
  сохраняются, ассерты переписываются под §4).
- Существующие тесты `text`/JSON — без изменений, остаются зелёными.

## 9. Риски

- Объём статического русского текста в коде — вынесен в `explain.go`
  (const-мапы/функции), render.go остаётся структурным.
- «Легенда не совпадает с фактической семантикой проверки» — текст легенды
  сверен с README-таблицей «Проверки (6 тегов)»; при добавлении новых
  проверок легенду дополнять (не блокирует).
- FP у тегов вне ooo/lag (возможны в сторонних данных, в демо не
  вживляются) — ни пояснительного абзаца, ни вердикт-проблемы не порождают;
  для демо-скопа осознанно принято (precision виден в таблице).
